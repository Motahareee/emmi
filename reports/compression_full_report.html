Encoder Compression: PTQ and QAT on CLIP and MobileCLIP

Results through PTQ (dynamic, static, real-kernel) and QAT, branch encoder-compression

Research question

This didn't start as the question — it emerged from the results. The general version:

When does post-hoc compression substitute for purpose-built efficient architecture design, and when does it just trade one cost for another?

CLIP and MobileCLIP are a natural first testbed: same embedding space and task, same training lineage (MobileCLIP is distilled from CLIP, not derived by compressing it — see below), but one is a vanilla architecture and the other is hand-optimized for mobile latency. Concretely, we asked: can quantizing CLIP make it competitive with MobileCLIP on size, latency, and accuracy — or does MobileCLIP's architecture-level efficiency remain a real, uncompressed advantage?

Scope honestly: this is currently a case study of one architecture pair, on one CPU backend (ONNX Runtime, ARM), with one small proxy accuracy benchmark (CIFAR-10 zero-shot, not the field-standard OpenCLIP 38-dataset suite). Generalizing to other vanilla/efficient architecture pairs and hardware targets is what would turn this into the broader research question above, rather than one data point toward it.

Why these two models

CLIP (openai/clip-vit-base-patch32) is a standard Vision Transformer — almost entirely nn.Linear layers, no efficiency-specific design. MobileCLIP's image encoder ("MCi") is a hybrid CNN–Transformer built on FastViT: Conv2d-heavy early stages plus structural reparameterization (multi-branch training blocks that collapse into a single efficient conv path at inference), purpose-built for mobile latency. The two are connected through training, not architecture — MobileCLIP is distilled from an ensemble of CLIP models via "multi-modal reinforced training," not derived by compressing CLIP's weights.

This matters directly for compression: CLIP is "vanilla" and has plenty of redundancy for generic compression techniques to find. MobileCLIP is already hand-optimized for efficiency before we touch it — and because our PTQ only targets nn.Linear (PyTorch's native quantization kernels don't cover Conv2d), MobileCLIP's Conv-heavy image tower has structurally less surface area for this specific technique to compress.

The whole motive: MobileCLIP's efficiency is a hardware claim, not just an architecture claim

MobileCLIP's published numbers aren't measured on a generic CPU -- they're measured on iPhone's Neural Engine via Core ML. That's the entire premise this investigation is testing: MobileCLIP's "efficiency" is a claim about specific mobile silicon, not about architectures in general. Off that hardware, on whatever CPU a given edge deployment actually has, does MobileCLIP's advantage still hold -- or is it specific enough to Apple's Neural Engine that a compressed vanilla model (CLIP) can match or beat it on more ordinary hardware? This is why the comparison in this report is never "MobileCLIP vs CLIP" in the abstract -- it's "MobileCLIP vs CLIP, on the hardware we actually have."

On Apple's Neural Engine, MobileCLIP-S0 is ~3.9x faster than CLIP ViT-B/32 (1.5ms vs 5.9ms) with 7.6x fewer parameters -- the published result. On generic x86 CPU, measured here with identical settings for both models, the ranking inverts: MobileCLIP is ~1.8x slower than CLIP (1853.8ms vs 1012.9ms min) despite being 7.6x smaller. We then confirmed this directly, not just by citing the paper: converting both image encoders to Core ML (benchmark_coreml_mac.py) and running them on a real Apple Silicon Mac gives MobileCLIP a 4.44x speedup over CLIP (1.37ms vs 6.07ms) -- matching the paper's claimed direction almost exactly, on our own hardware, not just their iPhone. This isn't a quantization or pruning artifact -- it's the plain, unmodified fp32 models, before any compression technique in this report ever touches them. MobileCLIP's depthwise convolutions and RepVGG-style reparameterized stem are architecturally efficient in FLOPs, and that FLOPs reduction pays off on specialized mobile silicon (Core ML's ANE execution path has dedicated, heavily-optimized depthwise/grouped-conv kernels) -- but FLOPs are not latency, and PyTorch's generic CPU Conv2d kernels aren't similarly optimized for grouped/depthwise operations the way large, regular, cache-friendly matmuls (CLIP's entire architecture) are. Every "MobileCLIP resists compression's latency win" result later in this report (quantization making it slower, Conv-pruning barely moving latency) is downstream of this one fact, confirmed with our own measurements before any compression technique is applied.

Plan: three quantization variants

VariantWhat it doesStatus
Dynamic PTQ Weights quantized to int8 once, offline. Activations quantized live, per forward call, from that call's actual min/max. No calibration data needed. Done
Static PTQ Weights and activations quantized ahead of time, using fixed scale/zero-point computed once from a calibration pass over real data. No per-call quantization decision at inference. Done
Weight-only int8 Only weights go to int8; activations stay in float the entire time (no activation quantization at all). Common for LLM inference where memory bandwidth, not compute, is the bottleneck. Next

Method notes (read before trusting the numbers below)

  • Dynamic uses PyTorch's native torch.ao.quantization.quantize_dynamic (real int8 kernels, qnnpack/fbgemm backend).
  • Static is simulated (fake-quant): weights are genuinely stored as int8 (so the size numbers are real), but each forward call dequantizes them back to fp32 before the matmul, because PyTorch's real eager-mode static-quant pipeline (QuantStub/DeQuantStub + module fusion) assumes a quantization-friendly forward() that arbitrary HuggingFace/open_clip transformer code doesn't have. This means static's accuracy numbers are trustworthy, but its latency numbers reflect fp32 compute plus a dequantization pass, not a true int8 kernel.
  • All latency numbers: 30 timed forward calls after 5 warmup calls, 4 CPU threads pinned, on this sandbox's CPU (ARM/aarch64). Reported as mean / min / std — min is the more noise-robust "perf floor" signal in a shared environment.
  • MobileCLIP's image and text wrappers share one underlying model object (see build_mobileclip_encoders) — sizes are reported once, not double-counted.
  • Calibration used 8 of 16 real COCO image/caption pairs; the remaining evaluation reuses all 16 (including the calibration 8) — a small, non-disjoint sample. Treat the static-vs-dynamic accuracy comparison as a first look, not a settled result; a larger held-out calibration set is the natural next step.

Finding 1 — size compression tracks architecture, not brand: CLIP compresses much further (2.57x) than MobileCLIP (1.38x) because CLIP's ViT is almost entirely nn.Linear, while MobileCLIP's Conv2d-heavy FastViT stages are untouched by this technique. MobileCLIP being "already efficient" isn't the (only) reason it compresses less — it's specifically that less of it is eligible for Linear-only PTQ.
Finding 2 — CLIP got reliably slower after dynamic quantization, confirmed across two runs with proper methodology (30 repeats, pinned threads, mean/min/std): 387±20 ms → 511±22 ms. Tight, consistent distributions on both sides — this is a real effect, not noise. Dynamic quantization pays a live min/max-and-quantize cost on every forward call; for CLIP's layer shapes and this batch size, that overhead outweighs the int8 matmul savings.
Finding 3 — MobileCLIP's first-run "2.8x slower" result was a noise artifact, not a real regression. The original run's orig-latency measurement had std (870 ms) nearly as large as its mean (1288 ms) — almost certainly one contaminated outlier call. The min-to-min comparison (739 → 721 ms) is a more reliable read: roughly latency-neutral.

Finding 5 — static PTQ, as implemented here, does not show a latency win over dynamic, and that's expected given the simulation. This implementation dequantizes the full int8 weight matrix back to fp32 on every forward call (there's no true int8 matmul kernel wired up), so it's doing strictly more floating-point work than the unquantized baseline: an elementwise dequant pass, plus the same fp32 matmul the original model already did. The accuracy numbers above are trustworthy — they reflect the real rounding/clipping error a static int8 kernel would introduce — but the latency numbers here measure simulation overhead, not the latency a real static-quantized deployment would actually see.

Real Static PTQ: genuine int8 kernels via ONNX Runtime

Both PTQ variants above ran in PyTorch eager mode, which couldn't show a trustworthy latency number because there was no real int8 kernel involved (dynamic pays live overhead; simulated static dequantizes back to fp32 before computing). The industry fix: export the model to a fixed computation graph (ONNX) first, then quantize that graph using the runtime's own tooling — the ambiguity that breaks PyTorch's eager-mode static quantization on transformer code doesn't exist once the model is a flat, explicit op sequence.

Scope: image encoders only. CLIP's text encoder hit an unrelated bug in a transformers internal function (masking_utils.create_causal_mask indexes a traced tensor incorrectly) during ONNX export — a library tracing issue, not a quantization problem. Exporting used PyTorch's legacy TorchScript-based exporter (dynamo=False); the newer default exporter produced a malformed graph (duplicate output name) on both models tested.

Finding 6 — CLIP finally shows the real latency win we were looking for: comparing the noise-robust min times, 563.2 → 221.4 ms is a genuine ~2.5x speedup. This is the first result in this whole investigation where quantization actually made inference faster, and it required a real int8 kernel to show up — confirming the diagnosis from the dynamic/simulated-static results: the *technique* works, PyTorch eager mode on this hardware was the wrong place to measure it.
Finding 7 — but accuracy dropped more than our simulation predicted (0.823 here vs. 0.986/0.839 for dynamic and 0.986/0.838 for simulated static). Quantizing the entire graph end-to-end (every Conv/MatMul input and output, not just Linear weights) compounds rounding error across many more quantize/dequantize boundaries than our simulation accounted for — visible directly in the node counts below: 432 QuantizeLinear + 631 DequantizeLinear nodes were inserted into a graph that only had 98 actual compute ops (97 MatMul + 1 Conv) to begin with.
Finding 8 — MobileCLIP's static quantization essentially broke the model (cos_sim 0.045 — indistinguishable from noise) and got slower, not faster. Initial hypothesis: ONNX Runtime's default per-tensor weight quantization is a known failure mode for Conv-heavy networks (119 Conv ops here), where different output channels can have very different weight magnitudes that one shared scale can't represent well. Testing this hypothesis is Finding 8b below.

Finding 8a — CLIP's real fix: per-channel weights + restricting quantization to Conv/MatMul/Gemm together push cos_sim from 0.823 to 0.946 while keeping the ~2x latency win (451→222 ms). Restricting op types leaves all elementwise/normalization math in fp32 (beyond what the quantizer's default named-op exclusions already skip), which turns out to matter more than the per-channel weight change alone (0.835). This is the config worth calling "the answer" for CLIP.
Finding 8b — neither fix touched MobileCLIP (0.045 → 0.113 → 0.098, still noise-level throughout, and still slower not faster in every config). This rules out "per-tensor weight granularity" and "normalization expressed as unfused ops" as sole explanations — the true cause is concentrated somewhere more specific. Rather than keep guessing at global settings, the next section isolates it directly: quantize one layer at a time and measure which one(s) actually cause the collapse.

Per-node sensitivity sweep

Quantized one Conv/MatMul/Gemm node at a time (all 128 candidates in MobileCLIP's image encoder, everything else left fp32), measured cos_sim against the true fp32 output for each. The result was a clean, decisive signal rather than a diffuse problem:

Finding 8c — two specific nodes, not a general architecture problem. There's a cliff between the two worst nodes (negative/near-zero cos_sim — actively destructive) and everything else (≥0.91, mostly ≥0.97). Both worst offenders sit inside stem.1, the second stem block, and are the two parallel branches of what looks like a structural- reparameterization ("RepVGG-style") block — a k×k kernel branch (conv_kxk) and a pointwise-scale branch (conv_scale). Notably, stem.0's equivalent branches are fine (0.972, 0.998) — this is specific to stem.1, likely an unusually wide weight or activation range in that particular layer that int8's 256 levels can't represent without the real signal getting swamped by quantization noise.
Finding 8d — excluding just those two nodes recovers most of the accuracy: re-running with nodes_to_exclude set to those two node names (everything else still quantized, per-channel + Conv/MatMul/Gemm-only) brings MobileCLIP's cos_sim from 0.098 → 0.754 — confirming the diagnosis precisely. Latency is still not a win (fp32 556 → int8 782 ms, min) — unlike CLIP, MobileCLIP hasn't shown a genuine speedup in any config tried, which is a separate open question from the accuracy one this sweep answered. Compression holds at 3.59x (43.7 → 12.2 MB) since only 2 of 128 candidate nodes are now excluded.
Finding 9 — a correction to the dynamic/simulated-static results above: this export revealed CLIP's and MobileCLIP's image encoders are genuinely 335.3 MB and 43.7 MB (fp32), not the 335.2 MB / 286.0 MB reported earlier. CLIP's number was already right; MobileCLIP's wasn't — the earlier measurement used the wrapper's full state_dict(), which (because image_encoder and text_encoder share one underlying model object) also counted the entire text tower, even though encode_image() never touches it. The ONNX export only traces what the image forward pass actually uses, so 43.7 MB is the true image-only footprint. MobileCLIP's image encoder is dramatically smaller than we thought — which also means its earlier 1.38x dynamic-PTQ compression ratio was measuring the wrong denominator (the shared model's total size, not the image path's actual size).

Answering the research question

Everything above measures a model against its own fp32 output (cos_sim) — useful for diagnosing what quantization breaks, but it never says whether either model's embeddings are actually good for anything. To answer "can quantized CLIP match MobileCLIP," we needed one more measurement: real task accuracy, independently, for both models — zero-shot CIFAR-10 classification ("a photo of a {class}" prompts, nearest-embedding classification), the standard CLIP evaluation protocol at small scale.

ModelZero-shot CIFAR-10 accuracy
fp32 CLIP92.0%
quantized-image CLIP (best config) + fp32 text84.0%
fp32 MobileCLIP94.5%
Finding 10 — no, quantized CLIP does not match MobileCLIP. Quantizing CLIP's image encoder costs a real 8-point accuracy drop (92.0% → 84.0%), and even before quantization, full-precision CLIP (92.0%) was already slightly behind MobileCLIP (94.5%) on this task — despite MobileCLIP's image encoder being roughly 7-8x smaller. Putting the full investigation together: MobileCLIP wins on both size and accuracy, unquantized. Quantized CLIP only wins on raw latency (Finding 6's ~2x speedup, which even beats fp32 MobileCLIP's own latency) — and it wins that one thing at a real accuracy cost. Compression does not let the vanilla architecture substitute for the purpose-built efficient one here; it trades one advantage (speed) for another cost (accuracy), rather than closing the gap outright.

What this actually tells us

The full arc across four implementations makes a coherent story. Dynamic and simulated-static (PyTorch eager mode) agreed with each other on accuracy but couldn't demonstrate a real latency win, because neither involved genuine int8 compute. Real static quantization via ONNX Runtime finally shows the latency win the size reduction promised for CLIP (~2x, and up to 0.946 cos_sim with the right config), while MobileCLIP's default-config collapse turned out to be caused by two specific layers, not a general architecture incompatibility — excluding them recovered accuracy from 0.098 to 0.754. "Quantize it" is not one operation with one outcome, and a model-wide failure doesn't mean the whole architecture is unquantizable — both CLIP and MobileCLIP needed real per-model investigation (op-type restriction for CLIP, per-node sensitivity analysis for MobileCLIP) before the actual achievable trade-off became visible, and that investigation process is itself part of what a fair CLIP-vs-MobileCLIP compression comparison needs to report, not just the final numbers.

QAT: Quantization-Aware Training

Fourth technique. Unlike PTQ (quantize an already-finished model), QAT fine-tunes with fake-quantization in the loop, so gradients see the rounding/clipping noise and weights adapt to be robust to it. Implemented via a straight-through estimator (STE) for gradients through round() (forward: rounded value; backward: treated as identity), fine-tuned via distillation against the frozen fp32 model (minimize 1 - cosine_similarity between student and teacher output) since we don't have either model's original training data or labels. Unlike the ONNX static-quant path, this is pure PyTorch autograd, so it isn't blocked by the text-encoder export bug — both towers get QAT here.

Finding 11 — contrary to the usual expectation, this QAT implementation didn't beat PTQ on image accuracy, even after refinement. Doubling training data (64→128 images) and switching to per-channel weight quantization (the same fix that helped PTQ) moved MobileCLIP's image cos_sim meaningfully (0.554 → 0.631) but not past PTQ's tuned result (0.754); CLIP barely moved at all (0.830 → 0.824). Worth being precise about what this does and doesn't show: it's not evidence that "QAT is worse than PTQ" in general — PTQ's numbers came from real, iterative debugging (per-node sensitivity sweep, architecture-specific op restriction) that this QAT implementation hasn't received yet, and QAT here is trained on a tiny fraction of the data a real QAT recipe would use. It is evidence that a naive QAT pass doesn't automatically outperform a well-tuned PTQ pipeline just by virtue of being QAT.
Finding 12 — QAT's genuine, consistent advantage is text: 0.900–0.909 vs. PTQ's 0.838–0.839 for CLIP, in both QAT runs. It's also the only technique in this whole investigation that reaches CLIP's text encoder at all, since it doesn't depend on the ONNX export path that's blocked there. If text-side quantization matters for a given deployment, QAT is the only option on the table right now, not just the better one.

The real-accuracy check that changes everything: QAT and pruning-recovery, re-examined

Every QAT/pruning number above is cos_sim — how close the compressed model's output is to its own fp32 output on the fine-tuning-adjacent COCO domain. Following the same discipline that answered the CLIP-vs-MobileCLIP question earlier (real zero-shot CIFAR-10 classification, not cos_sim), we checked what QAT's held-out cos_sim scores actually translate to on a genuinely different domain.

Finding 13 — QAT collapses real accuracy to near-chance on BOTH models (35–37% for CLIP, 34.0% for MobileCLIP — barely above the 10% random-chance floor for CIFAR-10's 10 classes), despite cos_sim scores that looked reasonable, especially for CLIP (0.82, in the same range as PTQ's 0.946). Reproduced across four independent QAT runs for CLIP (37.0%, 37.0%, 37.0%, 35.0%) — not noise. Cos_sim doesn't even correctly rank which model's QAT is worse: CLIP's cos_sim (0.82) is much higher than MobileCLIP's (0.55–0.64), but their real accuracy collapses to nearly the same floor. The likely cause is domain mismatch: QAT is real gradient-based training, fine-tuned via distillation on only 128 COCO photos (a narrow slice of one visual domain), then evaluated on CIFAR-10 (32x32-native, single-object images) -- a genuinely different domain. Unlike PTQ (which touches no weights and can't overfit this way), QAT's fine-tuning can reshape the model toward whatever narrow data it was given, at real cost to out-of-domain generalization.
Finding 14 — the same divergence shows up independently in structured pruning's recovery step, confirming this isn't specific to QAT's fake-quant mechanism -- it's a general property of gradient-based recovery on non-representative data. Fine-tuning a pruned CLIP (30% of MLP channels removed) via the same COCO-distillation recipe:
ConfigHeld-out cos_simZero-shot CIFAR-10 accuracy
Pruned, no recovery0.51921.0%
Pruned + recovery fine-tuning0.646 (better)16.0% (worse)
Recovery fine-tuning made cos_sim better and real accuracy worse -- the exact same direction of divergence as QAT, now confirmed independently on a completely different compression technique. This is strong enough evidence to state as a general finding, not a one-off: gradient-based compression recovery is only as trustworthy as how representative its fine-tuning data is of the real deployment distribution -- with narrow, non-representative data, recovery doesn't just fail to help, it actively makes real generalization worse while making the wrong metric (cos_sim on/near the fine-tuning domain) look better. This is the single most important methodological finding of this investigation, and it directly explains why PTQ (no training, can't overfit) has been the most trustworthy technique throughout: its numbers never needed this kind of correction.

Cluster-scale validation: the domain-mismatch hypothesis, confirmed

Findings 13-14 predicted that QAT and pruning-recovery's collapse was a symptom of too little, too narrow fine-tuning data (128 COCO photos) -- not a fundamental flaw in either technique. Real GPU compute made it possible to test that directly: ~30x more/more diverse fine-tuning data (4000 train / 1000 held-out eval, vs. 128/64), a larger real zero-shot eval set (2000 CIFAR-10 images, vs. ~100-200), on an A40 GPU.

Finding 15 — the hypothesis was correct, and for CLIP the fix essentially worked. QAT on CLIP roughly doubled (35-37% → 74.15%) just from more/more diverse fine-tuning data, with no other change to the technique. Pruning-recovery flipped completely: at small scale it made things worse than no recovery at all (16% vs 21%); at real scale it does exactly what recovery is supposed to do, 2.5x better than no recovery (49.65% vs 20.05%). Both confirm Finding 14's general claim directly: gradient-based recovery's trustworthiness really is gated on fine-tuning data being representative of the deployment distribution, and this failure mode is fixable, not fundamental.
Finding 16 — MobileCLIP's QAT gap didn't close nearly as much (34.0% → 43.45%, vs. CLIP's 35-37% → 74.15%), and 49.65% for pruning-recovery is still far below the 92% fp32 baseline. More data was necessary but not sufficient. This points to at least two further levers, not yet tried: (1) MobileCLIP likely has an architecture-specific bottleneck analogous to PTQ's stem.1 finding — a per-layer QAT sensitivity sweep is the natural next diagnostic, same method that fixed PTQ. (2) Pruning ratio=0.3 may simply be too aggressive a cut for a first attempt; eval_pruning.py's own sweep showed cos_sim was still 0.842 at ratio=0.1 with no recovery at all, suggesting a lighter prune + the now-validated recovery process could land much closer to fp32. Both are open, in-progress follow-ups.

Finding 17 — recovered accuracy plateaus around 60-64% for ratio 0.1-0.2, then drops at 0.3; "prune less" alone doesn't close the gap to fp32. Even the lightest cut tested (10%, barely any compression -- 313.6 MB, essentially still the original model) only recovers to 63.65%, a 28-point gap from the 92% baseline. This means the prune ratio was not the main bottleneck capping recovery -- something about the recovery process itself (15 epochs, fixed lr=1e-4, pure distillation loss) is hitting a ceiling around 60-65% regardless of how much capacity was actually removed. Loss was still decreasing at epoch 15 for every ratio tested (never fully converged), which is why tuning the recovery process itself (more epochs/LR, or iterative pruning) is the next thing to try, not further ratio sweeping.
Finding 18 — more epochs made recovery worse, not better; overfitting, not under-training, was closer to the truth. Re-ran ratio=0.1 (the best config from the sweep) with 40 epochs instead of 15, same everything else. Training loss kept dropping the whole time (0.0162 → 0.0077, never plateaued) -- but held-out cos_sim dropped (0.908 → 0.895) and real zero-shot accuracy dropped (63.65% → 58.75%). The training loss curve alone was actively misleading here: it looked like the model kept improving right up to epoch 40, while generalization was quietly getting worse the whole time. 15 epochs wasn't under-trained -- it may already be past the useful point. This rules out "just train longer" as the fix for the ~60-64% ceiling; the next candidate is iterative pruning (remove a little, fine-tune, remove more, repeat), which the literature suggests preserves substantially more accuracy than one-shot pruning at the same final ratio.
Finding 19 — iterative pruning didn't beat one-shot pruning either, at the same final compression. 3 steps of ~11.2% each (5 epochs fine-tuning between steps, 15 at the end, compounding to the same ratio=0.3 total) landed at cos_sim=0.867 and 47.95% zero-shot accuracy -- statistically indistinguishable from one-shot's 0.866 / 49.65% (same size too: 270.4 vs 270.3 MB). Two independent negative results now (more epochs, and iterative scheduling) point the same way: the ~50-64% ceiling likely isn't about how the pruning/training is scheduled at all. More likely candidates, not yet tried: the L2-magnitude channel-importance criterion itself may be too weak (gradient-based/Taylor importance is the standard stronger alternative), or the pure feature-distillation recovery loss (cosine similarity to the teacher's embedding) doesn't directly optimize for the classification decision boundaries that zero-shot accuracy actually depends on.
Finding 22 — Taylor/gradient-based channel importance does not beat L2-magnitude either, at the same ratio=0.3. One forward+backward pass of CLIP's own contrastive loss on a 256-image calibration batch, scoring each MLP channel by its actual effect on that loss (compute_taylor_importance), gave cos_sim=0.884 / accuracy=46.70% after recovery -- statistically indistinguishable from L2-magnitude's 0.866 / 49.65% (if anything, marginally worse on the metric that matters). This is now the third independent negative result after more epochs (Finding 18) and iterative scheduling (Finding 19): none of "train longer," "prune gradually," or "score channels by loss-sensitivity instead of weight-size" move the ~50-64% ceiling. The common thread across all three is that they all still use the same recovery objective (feature-distillation: 1 - cosine_similarity to the frozen teacher's embedding) -- increasingly the most likely remaining culprit is that this objective doesn't directly optimize for the classification decision boundaries zero-shot accuracy actually depends on, rather than anything about the pruning step itself.
Finding 23 — MobileCLIP's QAT gap isn't about which layers get quantized, it's that training actively makes it worse. Only 5 of MobileCLIP's ~795 image-encoder leaf modules are ever exercised as nn.Linear during a real forward pass (the 2 attention blocks' qkv/proj + the final head.fc projection) -- convert_to_qat only wraps nn.Linear, so this tiny fraction is literally the entire fake-quant scope; the other ~790 modules (all the RepMixer/ConvMlp Conv2d stages) stay fp32 throughout. Measuring the pure, untrained damage from fake-quantizing just those 5 layers (no fine-tuning at all) gives 68.5% zero-shot accuracy -- close to the fp32 baseline of 94.5%. But the actual QAT-trained result (15 epochs, 4000 images, cluster-scale) is 43.45% -- worse than doing nothing. Contrast with CLIP, where the same untrained-fake-quant probe (all Linear layers, i.e. virtually the whole network) collapses to 14.0% from a 92.0% baseline, and QAT training recovers that all the way to 74.15% -- training clearly helps there, because it has real damage to repair. convert_to_qat only makes the wrapped layers trainable (everything else stays frozen, per this project's freeze_base=True convention), so MobileCLIP's "QAT" run is gradient descent over just 5 layers' weights against a distillation loss, with nothing badly broken to begin with -- the same overfitting pathology as Finding 18 (pruning-recovery got worse with more epochs), not a quantization-coverage problem. This reframes the open question: not "which MobileCLIP layer is most sensitive to quantization" (Task #4's original framing) but "why does distillation fine-tuning over a narrow, already-fine parameter subset drift away from good generalization instead of leaving it alone."
Finding 24 — relational/contrastive distillation performed WORSE than plain cosine distillation, not better, and worse than doing no recovery at all in the same run. Same ratio=0.3, same 4000/1000 split, same 15 epochs, only the recovery loss changed: cos_sim=0.683 / accuracy=16.30%, vs. cosine distillation's 0.866 / 49.65% -- and vs. this run's own no-recovery baseline of 20.05% (recovery training made it worse than not recovering at all). Training loss fell smoothly throughout (3.71 → 0.06), so the objective was learned successfully -- this is a generalization failure, not an optimization failure, and the likely culprit is a real confound rather than the relational hypothesis itself being wrong: the training loop never reshuffles data between epochs. Cosine distillation is per-example and doesn't care about batch composition, but relational distillation's entire training signal comes from which other captions share a batch -- with the same ~62 fixed batches repeated across 15 epochs, the student can learn a degenerate solution tailored to that one fixed negative-pairing structure, without producing embeddings that generalize to arbitrary text (like CIFAR-10 class prompts) at test time. This would produce exactly the observed pattern (falling train loss, collapsing real accuracy). Before concluding the relational-objective hypothesis is wrong, the controlled next step is adding per-epoch batch shuffling and rerunning -- this result doesn't yet rule out the hypothesis, it rules out this specific unshuffled implementation of it.
Finding 25 — with the shuffling confound controlled for, relational distillation genuinely underperforms cosine distillation; the recovery-objective hypothesis is not confirmed. Same shuffled code, same ratio=0.3, same 4000/1000 split: cosine distillation reaches cos_sim=0.878 / accuracy=47.55% (essentially unchanged from the original unshuffled 0.866 / 49.65%, confirming cosine was never sensitive to batch order, as expected for a per-example loss); relational distillation reaches only cos_sim=0.684 / accuracy=20.55% -- shuffling moved its accuracy from 16.30% to 20.55%, ruling out Finding 24's confound theory as the primary cause, but nowhere close to closing the gap. Relational loss's training floor is also ~14x higher (0.22 vs cosine's 0.016) -- matching a full softmax distribution over 64 in-batch items is a harder target to fit than matching one embedding's direction, and doesn't converge as tightly in the same 15-epoch budget. Best current explanation: relational distillation bakes in more of the *training domain's* structure (COCO caption semantics, and which captions happen to co-occur in a batch) than cosine distillation does, making it more brittle to the same domain-mismatch problem that has been the central theme of this investigation (Findings 13-16) -- not less brittle, as the original hypothesis proposed. The simpler, more constrained objective turns out to be the more robust one. This closes the recovery-objective thread with a clean negative result rather than confirming it; the ~50-64% ceiling for cosine-distillation pruning-recovery remains unexplained after four independent interventions (epochs, scheduling, importance criterion, recovery objective).

Linear vs Conv: which compression techniques apply where

CLIP's ViT is built entirely from nn.Linear layers; MobileCLIP's FastViT trunk is mostly Conv2d (depthwise 7x7 token-mixers, 1x1 pointwise MLPs, a RepVGG-style multi-branch stem) with two small attention blocks at the end. This isn't a cosmetic difference -- it changes which compression techniques are even applicable, and it's the likely structural reason this investigation's compression results have consistently been stronger on CLIP than on MobileCLIP, independent of any specific tuning issue.

Linear (CLIP)Conv (MobileCLIP)
QuantizationUniform: one weight matrix, one per-row scale. Works cleanly everywhere — this is why CLIP's PTQ/QAT numbers are the cleanest results in this report. Same idea, per-channel — but RepVGG-style multi-branch stem blocks (stem.1/conv_kxk) are uniquely fragile to quantize (Finding 8/9); no Linear-only architecture has an analogous failure mode.
Structured pruningRemove MLP intermediate-width channels (fc1 rows / fc2 columns) — purely internal to one block, safe, implemented (Findings 14-19). Remove ConvMlp.fc1/fc2 1x1-conv output/input channels — same safety property, same removal logic (just 4D weight tensors instead of 2D). Implemented below (Findings 20-21) — behaves very differently from the Linear case.
Low-rank / kernel decompositionFactor W ≈ U @ V, rank r << min(in,out) — not yet implemented. Depthwise-separable decomposition (split a full k×k conv into depthwise + pointwise) or spatial-rank factorization (k×k as k×1 + 1×k) — arguably already "spent": MobileCLIP's efficiency is this technique, applied at design time rather than as a post-hoc compression step. There's less redundancy left to extract.
Width pruningAttention heads / embedding dim — deliberately avoided (cascades through the residual stream and every layer). Whole-filter pruning of the depthwise/stem convs — same cascading problem, worse: RepVGG-style reparameterized branches specifically resist any per-branch edit before they're fused. Not attempted.

The practical upshot: CLIP has one clean, uniform lever (Linear) that every technique in this report applies to directly. MobileCLIP's efficiency already comes partly from Conv-specific decomposition tricks baked into its architecture, so there's structurally less slack left for further compression to find -- independent of whether the specific fine-tuning recipe is tuned well.

Low-rank approximation (fourth and final technique)

Factors each MLP weight matrix via truncated SVD into two smaller matrices (emma/model_compression/lowrank.py) -- the mathematically optimal rank-r approximation before any fine-tuning, same recovery recipe as pruning for a direct comparison. See that file's docstring for the compression breakeven math: for CLIP ViT-B/32's 768↔3072 MLP shape, a two-matrix factorization only nets a size reduction below rank<614 (ratio>~0.2) -- smaller ratios actually INCREASE parameter count, confirmed directly (ratio=0.1 measured at 362.1MB, LARGER than fp32's 335.2MB, before this was even tried with recovery).

Final synthesis: answering the research question with the strongest numbers found

This report opened by asking whether MobileCLIP's efficiency is a hardware-specific claim, and whether compressing vanilla CLIP could close that gap on hardware where MobileCLIP's advantage doesn't apply. Both questions now have direct answers, not estimates:

The hardware claim is confirmed on real hardware, both ways. MobileCLIP is 4.44x faster than CLIP on an actual Apple Silicon Mac via Core ML (matching the paper's ~3.9x iPhone claim) -- and 1.8x SLOWER than CLIP on generic x86 CPU, the same two unmodified fp32 models, only the hardware changed. MobileCLIP's efficiency is real, but it is Apple-silicon-specific; on ordinary CPU hardware, CLIP is already the faster model before any compression is applied at all.

Compression closes most of the remaining accuracy gap on CPU, with real size and latency wins too. The strongest result across all four techniques tried:

No single technique wins on every axis. Pruning with the best criterion found (Hessian importance + global ranking) is the strongest when accuracy matters most -- at ratio=0.1 it gets within 2.15 points of full precision, requiring NO recovery fine-tuning at all, with a real (if modest) size and latency win. Quantization (PTQ alone, or QAT+PTQ combined) is the strongest when size and latency matter most -- 3.68-3.94x smaller and 2-2.56x faster, at a larger but still real accuracy cost. Low-rank approximation works but is dominated by pruning at every compression level tested here. On MobileCLIP, the same large-data + early-stopping recipe closes its pruning gap almost as completely (83.60% at ratio=0.1, Finding 30) -- but its QAT gap only partially closes (Finding 32), and its latency never meaningfully improves under any technique (Finding 20), because the actual compute bottleneck (depthwise convs, RepVGG stem) is architecturally outside every technique's current scope.

Bottom line: on generic CPU hardware, properly-recovered pruned CLIP doesn't just approach MobileCLIP's accuracy -- it operates in the same range as MobileCLIP's OWN real, measured CPU numbers (MobileCLIP fp32: 94.5% accuracy, but 1.8x slower than CLIP fp32 at that accuracy). Compressed CLIP at 89.85% accuracy, 1.07x smaller and 1.05x faster than ITS OWN fp32 baseline, is a genuinely competitive alternative to MobileCLIP specifically on hardware where MobileCLIP's Apple-silicon-tailored efficiency doesn't transfer -- which was the entire motivating question.

What this investigation deliberately did not do

  • Attention and embedding-width pruning/low-rank -- every technique in this report only ever touched the MLP's intermediate width, the one dimension structurally guaranteed not to cascade through the residual stream. Attention head dimensions and the shared embedding width are real, larger, unexplored levers -- left alone specifically because they're riskier (a change there touches every layer at once, not one local block) and would need their own investigation into what breaks and how much recovery data that requires.
  • MobileCLIP's actual compute bottleneck -- every technique applied to MobileCLIP in this report (quantization, Conv-pruning) only ever touched its MLP/Linear layers, never its depthwise convolutions or RepVGG-reparameterized stem, which Finding 20/30 identified as the real source of its CPU latency. Closing MobileCLIP's latency gap would need a technique that targets those specific layers (e.g. depthwise-separable re-factoring, or a CPU-specific kernel), not more of what this report already tried.
  • Text-encoder real-kernel quantization -- blocked throughout by an unrelated transformers library bug in ONNX export (create_causal_mask), not something this investigation's techniques could fix. All real-kernel numbers in this report are image-encoder-only; QAT (fake-quant, not real-kernel) is the only technique that ever touched the text tower.
  • TinyCLIP and other third-party efficient-CLIP baselines -- would have been a useful external benchmark ("how close did we get to a professionally-executed version of this same idea") but needs separate model-loading infrastructure never built here.
  • Low-rank approximation on MobileCLIP -- SVD factorization as implemented here only applies to 2D (nn.Linear) weight matrices; MobileCLIP's MLP is Conv2d (4D weights), which would need a different factorization scheme (e.g. per-spatial-position SVD, or a tensor decomposition like Tucker/CP) not implemented in this pass.
